## 設定ファイルは必要ですか？

いいえ。設定がなければ、修正表モード、組み込み修正表、既定の日本語チェックを
使います。辞書モード、除外、独自語彙、表記方針が必要になったときに設定を追加
してください。

## どのモードを使うべきですか？

低ノイズな CI は修正表モードから始めます。文章や、単語リストを管理しても
未知の誤字を見つけたい場所には辞書モードを使います。`[[overrides]]` でパス
ごとに選べます。

## `fix` は未知語を書き換えますか？

いいえ。候補が一つの誤字と、機械的な日本語の文字幅・表記変換だけを適用します。
未知語と候補が複数ある誤字は、人が選べるよう残します。

## 許可する単語はどこへ追加しますか？

- チーム・製品用語：プロジェクト単語ファイル（既定は `ayame-words.txt`）。
- 複数の自分のプロジェクトで使う個人名：ユーザー単語ファイル。
- 設定内に意図を残したい誤字：`[words].ignore`。
- 推奨修正がある既知の誤字：`[corrections.words]`。
- 推奨表記がある日本語の別表記：`[japanese.variants]`。

## 大文字小文字を区別しますか？

英単語と修正表の照合では区別しません。修正時は一般的な大文字小文字パターンを
可能な限り保ちます。そのためプロジェクト・ユーザー単語には通常一つの表記だけを
入れます。

## 3 文字の未知語が報告されないのはなぜですか？

トークナイザーの `min-word-len` は既定で 3 ですが、辞書モードの未知語検出には
4 バイト以上という追加下限があり、全大文字の語も除外します。既知の修正なら、
より短い単語も報告できます。

## 識別子を理解しますか？

キャメルケースと頭字語の境界を分割し、記号とアンダースコアを自然な境界として
扱います。URL、メール、ハッシュ、UUID 風の値など、データらしいトークンも
除外します。

## `サーバ` と `サーバー` の両方を許可するのはなぜですか？

日本語の既定スタイルは長音あり・なしの強制ではなく、文書内の一貫性です。一方
だけなら許可し、同じ文書に両方があると少数側を報告します。方向を強制するには
`katakana-style = "long"` または `"short"` を選びます。

## 固定サイズでファイルを打ち切りますか？

既定の `max-file-size = 0` は無制限です。上限を設定した場合も、黙って無視せず
概要に除外件数を表示します。

## ネットワークなしで CI を実行できますか？

はい。チェッカー自身はネットワークを使いません。レジストリコマンドだけが HTTP
を必要とするため、先にキャッシュするか、辞書ファイルをプロジェクト内に置いて
相対パスで参照してください。

## 一つのエディターで複数の言語サーバーを使えますか？

クライアントが一バッファーの複数サーバーに対応していれば可能です。プログラミング
言語のサーバーを残し、ayame-spell を追加します。[エディター設定](./editors/)
の Helix と Zed の例では明示的に併用しています。

## LSP と CLI の結果は違いますか？

同じコアチェッカーと設定を使います。LSP のエディター初期化オプションで意図的に
検出設定を上書きした場合と、エディターが未保存のメモリ上テキストを確認している
場合は差が出ます。

## 最終設定を確認するには？

次を実行します。

```sh
ayame-spell config
```

プロジェクトルート、読み込んだユーザー・プロジェクト設定、既定値を含む最終 TOML
を表示します。
